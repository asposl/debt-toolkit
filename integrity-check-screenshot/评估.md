# 验证码模块与 GUI 接口评估

评估日期：2026-09-02  
评估范围：`GUI/modules/scraper/actions_captcha.py`、GUI 前台执行接口、已保存的验证码调试样本。  
本次不评估飞桨模型，也没有重新打包可执行文件。

## 一、当前结论

当前验证码源码已经切换到 ddddocr beta。点选验证码的生产路径已改为：

1. ddddocr 始终使用完整字集直接识别；
2. 提示图文字只用于过滤模型直接返回的字符，不再通过 `set_ranges` 限制 softmax；
3. 不再使用候选字集归一化概率兜底；
4. 原始置信度低于 `0.60`，或无法完成目标字的一对一分配时，直接判定本图不可靠；
5. 判定失败后沿用现有流程刷新验证码，不执行猜测点击。

这会降低单张验证码的“强行成功率”，但可以避免误点、错误提交和把低可信结果当成成功。按照当前用户要求，这是更合适的失败策略。

## 二、离线样本结果

使用 `GUI/output/验证码调试` 下两个法院验证码站点的 17 条样本，以 `tip.png` 作为目标字及顺序来源，`bg.png` 作为原图；没有使用旧的 `meta.json` 或历史中间结果作为真值。

| 指标 | 结果 | 说明 |
|---|---:|---|
| 样本数 | 17 | 两个法院验证码站点 |
| 检测到的字框 | 5～7 个/张 | 大多数样本为 6 个 |
| 高置信度完成目标分配 | 4/17 | 23.5%，仅表示源码完成了点击坐标分配 |
| 主动拒绝并等待刷新 | 13/17 | 76.5%，符合“不确定就换图”策略 |
| 识别耗时 | 约 0.73～1.23 秒/张 | 包含检测和多路预处理，未包含浏览器刷新等待 |

上述 23.5% 不能直接等同于最终正确率：保存样本的历史目录名和历史识别结果可能有误，且尚未逐字人工确认所有 `tip/bg` 对应关系。它可以作为当前实现的保守自动分配率基线。后续应新增人工确认的 `target_boxes.json`，分别统计“识别正确率、拒绝率、误点率和单张耗时”。

## 三、源码改动检查

主要改动位于 `GUI/modules/scraper/actions_captcha.py`：

- `_get_dddd_ocr()` 使用 `ddddocr.DdddOcr(beta=True, show_ad=False)`；
- `_rec_text_dddd()` 每次识别前恢复完整字符集，候选字只做结果过滤；
- `_rec_char_variants()` 删除候选集归一化兜底，不投出目标字时保持空票；
- `DDDD_REJECT_BELOW` 从 `0.25` 提高到 `0.60`；
- `_assign_click_boxes()` 的默认分配门槛提高到 `0.60`；
- 删除了生产路径使用的候选集归一化重打分函数；
- 失败后的 `_tianai_refresh()` 重试路径保持不变。

## 五、模块规模与维护性评估

当前 `actions_captcha.py` 约 1,813 行、79 KB、63 个函数，是 scraper 目录中最大的动作模块。对比：`actions_basic.py` 约 134 行，`actions_advanced.py` 约 173 行。当前文件同时包含以下职责：

| 职责 | 典型内容 | 维护风险 |
|---|---|---|
| 诊断与日志 | 日志 sink、调试目录、图片落盘、目录清理 | 改动容易影响 GUI 日志或磁盘输出 |
| ddddocr OCR | 模型单例、字符集、提示图识别、掩码、旋转、多路投票 | 模型策略和业务流程耦合 |
| 点选验证码 | 天爱 DOM 探测、字框检测、目标分配、点击和校验 | 站点 DOM 变化会影响 OCR 调试 |
| 滑块验证码 | 缺口检测、轨迹生成、拖动、校验 | 图像算法与浏览器动作混在一起 |
| 结果判定与重试 | 表单基线、结果差分、刷新、人工兜底 | 业务状态机较长，回归测试成本高 |
| 历史兼容动作 | 最高院旧字符验证码、江苏税务 | 与天爱流程没有共享足够上下文 |

### 是否需要拆分

需要拆分，评级为“中高维护风险”。理由不是单纯行数大，而是一个文件内存在多个变化频率不同、测试方式不同的边界：OCR 预处理可以离线测试，DOM 状态机需要浏览器测试，滑块算法需要图片样本，诊断落盘又属于运行基础设施。它们现在共享大量私有函数和全局状态，定位问题时需要通读较大范围代码。

但不建议立即进行一次性大拆分。当前公开动作入口很少，且 `async_func_dp.py` 和 `site_configs.py` 已经依赖这些入口；一次性搬迁容易引入 PyInstaller 收集、相对导入、全局单例和 GUI 日志注册方面的回归。

## 六、建议的渐进式拆分

建议保留 `actions_captcha.py` 作为兼容门面，只保留公开 action 和转发函数，内部按以下边界逐步搬迁：

| 新模块 | 迁移内容 | 第一阶段验收 |
|---|---|---|
| `captcha_diagnostics.py` | 调试目录、日志 sink、图片/JSON 落盘、清理策略 | GUI 日志仍实时显示，调试目录结构不变 |
| `captcha_ocr.py` | ddddocr 单例、tip 识别、字符预处理、投票、分配 | 离线样本结果与迁移前一致 |
| `tianai_captcha.py` | 天爱弹窗、点选流程、滑块流程、DOM 图片状态 | 浏览器冒烟通过，刷新和人工兜底不变 |
| `captcha_result.py` | 查询结果基线、结果出现判定、超时观察 | 不重复提交已完成的查询 |
| `legacy_captcha.py` | 最高院旧流程、江苏税务流程 | 旧接口导出路径不变 |

推荐顺序是先拆 `captcha_ocr.py`，再拆诊断模块，最后拆天爱状态机和旧流程。每次只移动一组函数，不同时改算法；每一步都运行 `py_compile`、离线样本和一个真实前台站点冒烟。

## 七、后续优先级

1. 先观察 beta + “不确定就刷新”在真实运行中的误点率和平均换图次数；误点率应优先于自动通过率。
2. 为保存样本补充人工真值文件，禁止使用 `solved`、`assign-fail` 等目录名作为准确标签。
3. 记录每个字框的原始识别结果、置信度、是否被候选过滤和最终点击结果，形成可复现实验集。
4. 在有足够样本后再校准 `0.60` 阈值；当前 ddddocr confidence 对错误字符也可能很高，不能只凭阈值数字推断真实概率。
5. 完成 OCR 模块拆分后，再考虑减少旋转变体或增加更适合核显笔记本的预处理，以控制耗时。
